# v0.2 Phase 2: task and target intent

Implements the approved Phase 2 request using the
[Phase 1 migration proof](v0.2-phase-1-compatibility.md). No frontend, estimator,
result protocol, generated-source or frozen v0.1 contract changes are authorized.
Work remains on `feature/v0.2-regression`; no commits are made.

## Implementation plan

- [x] Migration: add `0006_task_objectives`, preserving literal reflected defaults.
  Route only pending objective rebuilds through a dedicated FK-OFF connection,
  explicit BEGIN IMMEDIATE, pre/post FK checks, integrity check and rollback/finally
  restoration. Refuse downgrade rather than silently converting regression rows.
  Exercise the real production path with Phase 1 fault/crash/preservation fixtures.

- [x] Target policy: validate parsed numeric non-Boolean values; exclude missing
  targets, require observed values, accept constant/two-valued targets, reject
  infinities and integer-to-float64 precision loss. Preserve source bytes and
  current revision/replacement/stale-binding semantics.
- [x] Integration: reuse preparation grammar, expose contextual regression readiness,
  and explicitly block current Code/Run execution for regression. Historical Run
  readers continue using frozen v1 evidence. Binary-only Explore target presentation
  must fail explicitly for regression rather than misinterpret it.
- [x] Verification: focused RED/GREEN tests per task; full backend suite, Ruff lint,
  formatting and diff checks once at the final gate. No frontend/dependency changes.

## Review focus

Check fresh and released upgrades, all historical bytes/rows, FK restoration on
failure, exact JSON defaults, unknown/cross-task IR, all-missing/Boolean/unsafe
numeric targets, stale edits after replacement and regression execution rejection.

## Operational boundary

Stop application/workers and back up SQLite plus managed files before migrating.
From `backend`, run `python -m alembic upgrade head` with the configured workspace.
This is an offline migration, not support for live concurrent upgrades. Phase 1's
platform/power-loss coverage limits still apply. Production downgrade from the new
revision is deliberately refused; restore a consistent backup if rollback is needed.

## API behavior and compatibility

`POST /api/v1/projects` accepts `ml_objective: "regression"`; omission still means
`binary_classification`. The field is forbidden in metadata PATCH and protected
against ORM task changes. No second task column is stored. ORM-created regression
Projects also receive the correct empty IR; the released SQLite server default is
preserved unchanged for compatibility.

Dataset and Pipeline endpoints keep their current revision guards. A regression
target returns an empty class list and explicit `numeric` / `exclude_rows` intent.
At least one non-missing numeric observation is required; constants and two-valued
numbers are accepted. Missing rows are counted for future exclusion, never filled.
Integer precision checks compare each parsed integer with its float64 conversion;
exactly representable large integers are accepted. Object/Boolean/complex and
infinite targets are rejected. This is a policy on the existing parser's numeric
interpretation, not arbitrary-precision decimal parsing.

Replacement clears the current Data target and preserves the old recipe as stale.
Explicit reset creates new task-correct preparation intent; it never rebinds an old
recipe silently. Existing binary IR `0.1`, including its optional version default,
retains its reader and generator. New `0.2` requires task `regression`; unsupported
versions, cross-task payloads, positive-class fields, target imputation, binary
models and stratification fields are rejected. Feature operation grammar and
contextual invalid/dormant intent remain shared. Regression Code returns not-ready,
Run admission returns 422, and Explore returns an explicit not-yet-available error.
No regression source, Run, metric or new visual surface is produced.

## Verification and next boundary

The Phase 1 preservation/failure/crash wrapper now calls the actual production
`env.py` and `0006_task_objectives`. Its copied naive environment remains solely
for negative tests characterizing unsafe transaction/FK usage. Schema comparisons
permit only the approved objective constraint change; historical rows, JSON,
defaults, ownership and artifact bytes remain exact. Tests also cover relative
`+1` traversal, fresh/released upgrades, no-op/older traversal without FK-OFF,
readiness before/after upgrade, strict intent, numeric policies and API persistence.

Phase 3 must add the small model catalogue, regression estimator intent and
contextual model/split readiness checks before any later compiler/execution work.
Regression code generation, result dispatch, training, tracking/evaluation and
frontend task flows remain unimplemented. No v0.1 frozen document or golden is
changed. Final verification: `python -m pytest -q` passed all 543 cases (37 added
in Phase 2); Ruff lint passed and formatting found 72 files already formatted.
The 489 warnings are dependency deprecations, not test failures. The initial full
run exposed an old fresh-database test expecting downgrade from the new head;
it now asserts deliberate refusal and unchanged revision. Separate coverage retains
the original five migrations' downgrade path. Final diff checks passed.
