[`released_v01.py`](../../backend/tests/released_v01.py) builds a synthetic workspace

not use current Project/Run constructors or mutable application defaults. Future

The fixture has:

  IDs/request identities/sequence/revisions, terminal times, frozen IR/plan/package,

- A tiny real fitted preprocessing-plus-LogisticRegression artifact and a valid v1

  This is fixture construction, not a claim that its history was captured by an
  actual executor; existing real-execution tests cover that boundary.

Archived Python is taken from the pinned v1 numeric golden with only the three
fixture Dataset identity/size literals substituted. It is **not regenerated by
the current renderer** to seed history. A separate assertion compares the current
v1 renderer to that archived program. Independent fixed SHA-256 values pin all six
released golden files and their rendered outputs, even if both sides were edited.

`snapshot` captures every stored column value, including SQLite JSON text, all

## Migration investigation: three reproduced hazards

1. **Cyclic ownership with FK enforcement.** `projects` references its active
   Dataset; `datasets` and `runs` reference Projects, and Runs also reference the
   Dataset owner pair. Dropping/recreating the parent under FK ON fails. SQLite
   ignores `PRAGMA foreign_keys=OFF` inside an already-started transaction.
2. **Legacy sqlite3 DDL transaction behavior.** A SQLAlchemy transaction alone does
   not necessarily issue SQLite BEGIN before DDL in this environment. The naive
   batch rebuild fails but can leave `_alembic_tmp_projects` behind. An explicit
   `BEGIN IMMEDIATE` before any migration DDL is necessary for the tested rollback
   guarantees; SQLAlchemy's implicit transaction label is not enough.
3. **Reflected JSON default corruption.** The current Working Pipeline server
   default contains `:null`. Alembic's reflected text expression treats these
   substrings as bind-looking parameters and renders `"dataset"NULL` instead of
   `"dataset":null` during a naive rebuild. Schema preservation and an actual
   INSERT omitting `working_pipeline` both failed before the fix. Keep the trusted
   reflected SQL defaults as `sa.literal_column(...)` through `DefaultClause`
   on the table passed to `copy_from`; do not parse/rewrite stored JSON or change
   the expected default to accommodate the corruption.

These are migration design findings, not changes to the released application.
No existing assertion or golden was weakened.

## Proven candidate for Phase 2

[`sqlite_objective_rehearsal.py`](../../backend/tests/sqlite_objective_rehearsal.py)
copies the five actual release migrations into a temporary Alembic directory and
adds a **test-only** revision `phase1_objective_rehearsal`. It is deliberately not
discoverable by the application's Alembic configuration. Its env accepts one
externally owned connection and configures transactional DDL.

The tested sequence is:

1. Use an offline, disposable copy for rehearsal; production upgrade requires the
   application/workers stopped and a consistent SQLite plus managed-files backup.
2. On a dedicated migration connection, outside a SQLite transaction, set
   `foreign_keys=OFF`, verify it, and finish SQLAlchemy's PRAGMA-only transaction.
   Never change the normal application engine's FK-ON connect listener.
3. Issue explicit `BEGIN IMMEDIATE`, verify the driver's transaction is active,
   and reject pre-existing foreign-key violations without trying to repair them.
4. Run the selected Alembic upgrade traversal on that same connection. Reflect
   `projects`, preserve its trusted server-default SQL as literal expressions,
   and use `batch_alter_table(..., recreate="always", copy_from=table)`.
5. Replace only `ck_project_objective` with
   `ml_objective IN ('binary_classification', 'regression')`. Copy every existing
   column value using the batch INSERT/SELECT path. Do not rename the original
   parent first, transform Project recipes, or update historical Run JSON/files.
6. Validate `foreign_key_check` is empty and `integrity_check` is `ok` before commit.
   Alembic version advancement is inside this transaction, alongside DDL and data.
7. Commit only after validation; roll back on exceptions. Restore and verify
   FK ON after the transaction in `finally`, then dispose the dedicated engine.

The disposable upgraded schema accepts regression and rejects unsupported task
values. The full released schema/data/metadata is otherwise preserved, including
the valid JSON default and next-sequence default on a real new INSERT.

## Failure and recovery proof

[`test_sqlite_objective_rehearsal.py`](../../backend/tests/test_sqlite_objective_rehearsal.py)
uses real SQLite/Alembic operations rather than mocked migration results:

- Exceptions injected after CREATE, row copy, parent DROP, new-table rename,
  revision UPDATE and final integrity check restore the original rows/schema/head.
  The same connection is checked for FK ON and no open driver transaction. A retry
  then succeeds without cleanup or evidence repair.
- Deliberately broken ownership during the rebuild fails the pre-commit FK check
  and rolls back. Pre-existing corrupt ownership is refused with its original
  evidence unchanged.
- Fresh `base -> rehearsal head`, fresh released schema -> rehearsal head, populated
  released schema -> rehearsal head, and repeated no-op upgrade all succeed.
- A real child process exits via `os._exit(91)` immediately after `DROP TABLE projects`.
  Opening a new connection recovers the original SQLite journal state. The original
  revision and all data/artifacts are retained, and a clean retry succeeds.

The Phase 1 focused suites contain **35 passing cases**. Existing golden tests
remain byte-for-byte, with no line-ending normalization. Final full-suite and
quality-gate results belong in the implementation report; do not infer those
results solely from this focused proof.

## Phase 2 prerequisites and coverage limits

- Review this proof before authorizing Phase 2. Add a new production migration;
  never edit `0001..0005` or ship the test-only revision directory.
- The current production `alembic/env.py` creates its own connection. Phase 2 must
  implement/test the checked connection/transaction boundary there (or a small
  explicit migration runner), before that boundary enters the new revision's
  traversal. Toggling FK enforcement inside the revision alone is too late.
- Select the special SQLite path by the actual pending upgrade traversal, not a
  blanket global FK-OFF engine setting. Preserve ordinary upgrade behavior when
  the rebuild revision is not pending. Keep transaction ownership explicit.
- Wire this fixture's `upgrade head` preservation gate to the real new revision
  once it exists; test fresh/upgraded schema parity and the actual application
  startup/schema-readiness path. The test-only wider constraint is not application
  regression support or proof of future Pydantic/frontend contracts.
- Define safe downgrade policy separately: never silently convert regression
  Projects to binary or delete them to satisfy the old check. The Phase 1 test
  revision explicitly refuses downgrade; no downgrade safety claim is made.
- This proof covers the declared Windows/SQLite environment, default journal
  behavior and one controlled hard process exit. It does not simulate power loss,
  full disks, corrupt SQLite pages, every commit-error outcome, custom PRAGMAs,
  WAL/network filesystem configurations or live application writers.
- Fixture tracking associations are preserved domain records, not a reconstructed
  MLflow store. Existing tracking/execution tests remain the integration authority.
- No binary task conversion, IR/result version dispatch, catalogue, regression
  estimator or frontend workflow is implemented in Phase 1. Those remain later
  phases of the approved release scope.
