## Existing lifecycle and integration decisions

`services/pipelines.py` validates working intent. `services/code_preview.py` reads
the verified managed buffer, resolves a plan, renders source and hashes canonical
plan/source bytes with a final revision check. `execution/service.py` regenerates
at admission, compares reviewed hashes/revision, writes immutable IR/plan/source/
package artifacts, verifies publication and commits one Run under the Project
revision guard. `Coordinator` owns the workspace lease, executes the persisted
file, validates result/model outputs, publishes hashed artifacts and commits a
terminal state. Existing API list/detail/code readers inspect frozen evidence.
MLflow synchronizes afterward and reconciles independently on restart.

Binary assumptions are the temporary objective guards, binary IR/resolve/render
imports, result-v1 validator selection, and tracking's model name/positive class.
Replace these dispatch points, not the coordinator/storage architecture. Reusing
the package-v1 envelope is sufficient: its provenance map can freeze regression
task/IR/plan/result protocol identifiers without changing legacy packages.

The alternatives (a second executor/Run table or changing v1 result/compiler
contracts) would break the requested shared lifecycle and historical compatibility.
No public response needs fabricated binary fields. Regression summaries identify
their task and protocol; results retain the strict v2 shape. Legacy summaries and
results retain their original shape. `PipelineResponse.executable` remains the
legacy non-executing configuration endpoint marker; reviewed Code plus capacity
and immutable Run admission remain the actual execution authority.

## Review focus

1. Stale revisions, hashes or replaced Dataset bindings must never create a Run.
2. A v2 result must match frozen source/plan/protocol/population before success.
3. Missing, redirected or invalid models must not publish a successful result.
4. Historical task/protocol and tracking must not depend on current Project data.
5. MLflow retry/recovery must preserve terminal evidence and external association.

## Versioned admission and finalization

Preview and admission both call `load_ir(payload, project.ml_objective)`,
`resolve_for_version` and `generate_for_version`. Existing v1 implementations and
all source goldens remain untouched. A configured regression Pipeline now has
`configuration_ready=true` and `code_generation_ready=true`; missing model/split,
invalid features, stale Dataset, parser/environment mismatch and target issues
still block it. Public preview reports generator `mlstudio-python-v2`, returns no
partial source for incomplete intent, and never launches a process.

The existing Run request (request UUID, revision, source hash, plan hash) is
unchanged. Admission regenerates from the current verified source and compares
both hashes before publication. Current revision is checked before resolution and
again when allocating the Project-local Run sequence. Same-request retries return
the existing Run even after later Project edits or Dataset replacement; changed
inputs with the same UUID still conflict. Workspace ownership remains one local
attempt, with the existing cross-process lease and no queue.

Regression package provenance and summary add `task="regression"`,
`ir_version="0.2"`, `plan_version="0.2"`, `result_schema="mlstudio-result-v2"`.
IR, complete plan, exact generated Python, parser/environment context, Dataset
identity/fingerprint and expected population are frozen using the existing
artifacts and SQLite JSON fields. No migration or second Run table is introduced.
Binary package and summary shapes are unchanged.

Before launch, the coordinator verifies published inputs/package, validates the
plan version, checks the persisted plan bytes against the reviewed plan hash and
the source artifact identity against the reviewed source hash. It executes the
same persisted file using the existing isolated-argument subprocess adapter.
After exit it reverifies inputs/source and dispatches result validation by the
frozen expected plan/protocol. V2 checks expected source/plan hashes, task,
versions, Dataset/source interpretation, evaluation context and population; the
v1 validator remains unchanged. Unknown/mismatched results cannot become success.

The model policy is unchanged: a nonempty bounded regular managed file, no link/
junction redirection, hashed publication, then a terminal transaction. Production
does not unpickle a model to establish success. Actual sklearn integration tests
inspect only their own trusted fitted artifacts to prove complete preprocessing
plus regressor and dense/sparse behavior. This does not authenticate arbitrary
external model content or provide a subprocess security sandbox.

## Historical API and tracking

Existing `/api/v1/projects/{project_id}/code` and `/runs` POST/list/detail/code
endpoints are reused. Run summaries/results remain frozen dictionaries; regression
summary fields above and the v2 task/result discriminator make the evidence
task-aware without binary class or confusion-matrix placeholders. Unavailable R2
is null with its frozen reason; true zero and negative R2 remain values.

`RunResponse` adds nullable `result_error`. Known v1/v2 results remain in `result`.
Unknown or mismatched stored protocols return `result=null` plus a sanitized
unsupported warning while leaving SQLite/artifacts unchanged. Detection uses
frozen generator/summary/result context, never the current Project objective.
Existing artifact-integrity statuses remain response-only; retained known SQLite
metrics are still readable when the old Dataset source is missing or corrupt.
Historical Python is read exactly, never regenerated.

MLflow resolves the verified frozen execution plan for model/parameters, target,
split and preparation. Regression tags include task/result protocol; only its
MAE/MSE/RMSE and available R2 are logged, preserving zeros and negative values.
There is no positive-class, confusion-matrix or AUC access for regression. V1
tracking keeps its positive-class parameter and existing external associations.
The existing local artifact-containment checks and full plan/source/result
artifacts are retained; the fitted model stays managed locally with a hashed
`model_reference.json` in MLflow. MLflow is never authoritative Run evidence.

## Failure, recovery and Phase 6 boundary

The existing launch/timeout/bounded-log/process-ownership and shutdown paths remain
shared. V2 failure parsing accepts only its fixed task/protocol and stage whitelist,
not child messages. Missing/invalid output yields FAILED with no published result
or model reference. Terminal facts remain ORM-immutable. Interrupted attempts are
failed conservatively on restart and never resumed; owned orphan handling remains
unchanged. Tracking failures update only separate tracking fields and reconcile
without execution or model deserialization, preserving authoritative terminal facts.

Phase 6 must add task-aware frontend creation/configuration, result/history and
comparison presentation. Existing frontend views are not regression acceptance
surfaces yet. No regression comparison, new estimators/metrics, prediction storage,
Visual/Code Mode, AI, release packaging/version changes or deployment is included.
Compiler numerical/evidence limits from Phase 4 still apply: aggregate evidence
does not independently recompute metrics or prove held-out row membership, and
source determinism does not guarantee bitwise fitted models across hardware.
