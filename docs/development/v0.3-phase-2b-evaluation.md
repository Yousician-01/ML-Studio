# Code Mode Phase 2B: Evaluation bridge

Code Runs can report aggregate evaluation evidence to the existing Evaluate bench.
Execution stays in Code Mode; there is no automatic navigation after completion.
Use **Evaluate this Code Run** in captured output, or select **Code Runs** in
Evaluate. While a draft is active, opening Evaluate defaults to Code Runs; explicit
Visual Run deep links still select Visual Runs. Code evaluation defaults to the
latest completed execution, including attempts without reports, and supports
20-item historical pages and `?view=evaluate&source=code&code_run=<id>` deep links.

## Reporting API

Each new execution workspace contains a local `mlstudio_runtime.py`, independent
of importing the backend package in the configured interpreter:

```python
from mlstudio_runtime import (
    report_classification, report_regression, report_metric, report_output,
)

# Binary class order is explicit: [negative, positive]. Scalar types must match
# the observed labels. Scores, if supplied, increase toward the positive class.
report_classification(y_true=actual, y_pred=predicted, labels=[0, 1], scores=None)

# In a regression Project, use this instead:
# report_regression(y_true=actual, y_pred=predicted)

report_metric("custom_validation_score", 0.91)
report_output("selected_features", ["age", "income"])
```

Variable names, estimator identity and preprocessing are not part of the contract.
Classification labels must be distinct matching string, boolean, integer or finite
float scalar types. Unsafe integers use the existing decimal-string typed wire
encoding. Targets, predictions and optional scores must be matching one-dimensional
arrays of 1–100,000 values. Missing/non-finite values are rejected; regression
requires actual finite numbers, without string or boolean coercion. Metrics follow
existing definitions: binary positive-class precision/recall/F1 use zero-division
zero; AUC needs scores and both observed classes; RMSE is sqrt(MSE); R² is unavailable
for fewer than two samples or a constant target. Negative R² remains valid.

Newly created drafts include explicit reporting calls in their Code Mode baseline.
The visual compiler and historical visual source remain unchanged. Existing saved
drafts are never rewritten: add the appropriate call above using your own variable
names to opt in, then create a new execution. Existing Code Runs without reporting
remain inspectable with a **not reported** state; they are never rerun or inferred
from old `result.json` files or console text.

### Recovering older drafts

Reopening Code Mode loads the saved draft, rather than generating a new one. In
particular, drafts saved before Phase 2B retain their original source and can finish
execution without reporting. Refreshing Code or restarting the backend does not
upgrade them.

Use **Enable Evaluation Reporting** below the editor to request a read-only proposal
from `POST /code-drafts/{draft_id}/reporting-proposal` within the Project API. The
proposal uses the current editor source and saved draft revision. Recognized existing
reporting calls are left alone. Automatic insertion requires the executable AST to
match the preserved generated baseline; comments and formatting remain untouched.
Renamed variables, changed executable logic or unsupported syntax get a concise manual
example instead. No variable inference, execution or source regeneration is performed.

Review the diff and select **Apply and save reporting**, or cancel without changing
anything. The editor and revision must still match the reviewed proposal. Applying
uses the normal revision-guarded draft save and includes current unsaved editor text;
it leaves the baseline, originating visual configuration, snapshots and historical
Runs intact. If saving fails, the proposed editor text remains available as unsaved
text. Execute again to create a new Code Run with evaluation evidence. Intentional
omission remains supported and never causes an automatic rewrite.

## Artifact and lifecycle

The versioned JSON envelope is `mlstudio-code-report-v1`:

```json
{
  "schema_version": "mlstudio-code-report-v1",
  "evaluation": null,
  "metrics": {"custom_validation_score": 0.91},
  "outputs": {"selected_features": ["age", "income"]}
}
```

`evaluation`, when reported, contains `task`, `population.test`, `metrics`, and
either typed `confusion_matrix` with `roc_auc_unavailable_reason`, or
`r2_unavailable_reason`. It contains aggregate evidence only, without raw targets,
predictions, row identifiers or model objects. Reporting calls replace the stock
evaluation or the named custom value; multiple calls do not append raw data.

After process-tree cleanup, successful execution reporting is strictly validated
against the originating task frozen at admission. The exact validated bytes from
`workspace/code-evaluation.json` are published as `evaluation.json` under that Code
Run's artifact directory. The existing immutable finalization JSON records status,
schema version, SHA-256, size and workspace-relative reference. No migration is
needed; no raw reporting values are added to SQLite metadata. Reads verify source
and result integrity, enforce the schema again and never recompute results.

`GET /api/v1/projects/{project_id}/code-runs/{run_id}/evaluation` returns `status`
and a nullable `report`. States distinguish pending, execution incomplete, not
reported, invalid, available and unavailable/corrupt evidence. A zero exit code
only indicates execution completion; it does not imply evaluation availability.
Failed/cancelled attempts expose logs rather than partial success charts. Older
interrupted attempts retain the existing restart-recovery behavior.

Reports are bounded to 1 MiB. Each custom section allows 64 names (1–128 characters),
JSON nesting is limited to eight levels, lists to 256 items, objects to 64 keys,
strings to 8,192 characters and class-label strings to 1,024 characters. Duplicate
JSON fields, extra schema fields, invalid types and non-finite numbers are rejected.
Rendering uses plain React text; evaluation never loads pickle/joblib files.

## Interpretation and limits

Existing metric cards and the accessible TN/FP/FN/TP confusion matrix are shared
with Visual Runs. Only supported aggregates are charted. Custom metrics and bounded
JSON/text are displayed separately. ROC-AUC is supported with valid oriented scores;
ROC curves, prediction/residual plots and arbitrary custom charts are not added.

These are self-reported results from trusted arbitrary Python. Validation checks
structure and aggregate consistency, not the truth of user code. The originating
visual model, split and Dataset do not prove what manually edited Python used.
Code Runs therefore do not participate in controlled comparison/delta calculations.
No console parsing, MLflow synchronization, IR changes, new algorithms or execution
sandbox is introduced. Existing localhost and execution opt-in restrictions apply.

Manual acceptance: run modified classification/regression code, stay in the IDE,
open Evaluate, inspect the selected Code Run and its custom outputs, select an older
attempt, then remove reporting and verify a new attempt shows no stale charts.
